# Domain glossary

ruxia is a messaging app whose contacts are AI personas. The code, the GraphQL schema and
the collections speak English; the people who use it speak French, often. Each term is the
one the code uses, with the French it stands for. A term joins this table with the module
that introduces it. The specification is [docs/spec.md](docs/spec.md).

| Term (code)      | French                | Meaning                                                                                                                                                                                                                           |
| ---------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Member           | membre                | A person with an account on this ruxia; `members` holds its name, locale, avatar and settings. Its id is the janus account's.                                                                                                     |
| Role             | rôle                  | `admin` or `member`, held in janus's relations, never stored on the member. The last active admin cannot be demoted or disabled.                                                                                                  |
| Invitation       | invitation            | The only way in: an admin invites an address with a role; the invitee accepts with a name and a password. No sign-up.                                                                                                             |
| Disabled         | désactivé             | A member with `disabledAt` set: janus refuses its sessions and sign-ins until an admin enables it.                                                                                                                                |
| Viewer           | utilisateur           | The signed-in member as the session shows it: role, locale, second factor, passkeys, budget status.                                                                                                                               |
| MemberSettings   | réglages              | Language fr/en, push previews, voice auto-play, default persona, "remember without asking" (spec 4.16).                                                                                                                           |
| BudgetStatus     | budget                | Where the member stands this month (`viewer.budgetStatus`): spent, budget, percent, `alertedAt` (the in-app notice of the 80 % alert), `resetsAt`.                                                                                |
| Budget           | budget mensuel        | USD per member per calendar month in America/Toronto: its own (`setMemberBudget`) or the team default (`setDefaultBudget`, 20 until set). 0 allows no paid model.                                                                 |
| Usage            | consommation          | `usage(month)` and the admin's `teamUsage(month)`: cost and tokens per member and per model, figures only. The month is `YYYY-MM`.                                                                                                |
| Project          | projet                | A member's group of documents and conversations (`projects`): a name (80 characters), `instructions` (4,000) the model reads in every run of the project, and its documents. Owner-scoped; soft deleted for 30 days, then purged. |
| Document         | document              | A file of a project (`projectDocuments`): Markdown, plain text or PDF, with a `status` (PENDING, INDEXED, FAILED) and, when FAILED, an `errorCode` string. Not an attachment: it belongs to a project for good.                   |
| Chunk            | extrait               | A piece of an indexed document (about 800 tokens, overlap 100) with its 768-dimension embedding (`chunks`): what `search_project` finds.                                                                                          |
| Citation         | citation              | A passage a reply rests on: `MessageCitationPart { documentId, name, snippet, score }`, one per result of `search_project`.                                                                                                       |
| Model            | modèle                | An entry of the model catalogue (`models`): public id, provider (Claude or Ollama), label, capabilities, context window, prices.                                                                                                  |
| Enabled          | activé                | A model an admin allows conversations to use. Claude models start enabled; discovered Ollama models start disabled.                                                                                                               |
| Available        | disponible            | A model a send can reach now: always for Claude, for Ollama while the last probe saw its server up with the model installed.                                                                                                      |
| Probe            | sonde                 | The check of the Ollama server every 30 s (`OLLAMA_BASE_URL`), cached in Redis for 90 s, which also lists new installed models.                                                                                                   |
| Persona          | persona               | An AI contact a member creates (`personas`): name, avatar, tagline, personality (the system prompt), default model, tools.                                                                                                        |
| Visibility       | visibilité            | `PRIVATE` (the owner only) or `TEAM` (every member reads and starts it, only the owner edits; others duplicate it into a PRIVATE copy).                                                                                           |
| Catalogue        | catalogue             | The TEAM personas, read with `catalogue(filter)`; the admin features some and orders them (`setPersonaFeatured`, `reorderFeatured`).                                                                                              |
| Featured         | mis en avant          | A TEAM persona the admin placed (`featuredRank`) at the top of the catalogue. Making it PRIVATE again unfeatures it.                                                                                                              |
| Conversation     | conversation          | A member's exchange with one persona (`conversations`): model, title, snapshot of the persona, `activeLeafId`. Private to its owner, the admin included.                                                                          |
| Message          | message               | A node of a conversation's tree (`messages`): `parentId` links it to the message it follows; several children make branches.                                                                                                      |
| Run              | exécution             | The writing of one assistant answer, started by `sendMessage`; its id is the assistant message's id (`Message.runId` while STREAMING), held as `activeRunId` until it ends.                                                       |
| Active leaf      | feuille active        | The last message of the branch a conversation shows; the path from the root to it is what the model reads and the list pages.                                                                                                     |
| Persona snapshot | instantané du persona | The persona's name and avatar kept on the conversation when it starts, so it stays readable after a rename or delete.                                                                                                             |
| Attachment       | pièce jointe          | A file (image, PDF or text) a member uploads to send with a message; a message keeps a reference, never a URL (see "Attachments").                                                                                                |
| Memory item      | souvenir              | One fact (at most 500 characters) a persona remembers about a member (`memoryItems`), per persona and member, `source` MODEL or USER (see "Memory").                                                                              |
| Proposed action  | action proposée       | A write the model asked for through a `confirm` tool, kept in `proposedActions` until the member confirms or rejects it (see "Proposed actions").                                                                                 |

Modules: `accounts` (sign-in, second factor, passkeys, step-up), `members`, `invitations`,
`models`, `personas`, `conversations`, `memory`, `budgets`, `translations` and `system`. Operator scripts: `admin:create <email>` (issues an admin
invitation and mails it; `--print-link` prints the link), `db:sync`, `db:migrate`,
`schema:print`.

## Media

Files go through `@softistx/alxia-media` routes beside `/graphql`, over the private `S3_*` bucket (no URL ever leaves the API; the UI builds `/media/<kind>/<key>/<size>` on its own origin). Three kinds share the one mount (`appMedia`): `attachments` (below, under "Attachments"), `conversation-exports` (below, under "Branches, search, export and deletion") and `persona-avatars` (`PUT` and `GET`, no `DELETE`; png, jpeg or webp up to 2 MiB, at least 64 px a side). A `PUT` answers `{ key, contentType, size }`. The upload is re-encoded into PNG squares of 256 and 64 px and never stored, so its EXIF and GPS data are dropped: only `/media/persona-avatars/<key>/256` and `/64` are served (the bare key is 404). The key is the uploader's until a persona carries it, then read by the persona's readers. Limits: `media-uploads` 30 an hour per account (burst 10, fails open) and a quota of 50 files per member (402 `quota_exceeded`). An upload whose key cannot be recorded is removed at once. Files are otherwise kept: a deleted persona keeps its avatar.

## Runs

`sendMessage` writes the member's message (DONE) and an empty assistant message (STREAMING), makes `runId` the assistant message's id, sets it as the conversation's `activeRunId` and starts the run, which goes on whether or not the client stays. The answer is followed at `GET /runs/<runId>/events`, the second transport beside `/graphql` (after `/media`): the same viewer (`Authorization: Bearer`) and the `x-ruxia-client` header, and the answers are the API's JSON, `{ errors: [..] }`: 403 `auth.errors.client-header-required`, 401 `auth.errors.unauthenticated`, 403 `auth.errors.forbidden` (no role), 404 `conversations.errors.run-not-found`. The stream is `text/event-stream`: one frame per event, named after its type (`step-start`, `text-delta`, `thinking-delta`, `usage`, `error`, `done`, ...), with `id:` the event's position in the run (`1`, `2`, `3`, ...) and `data:` its JSON; a `: heartbeat` comment every 5 s while nothing is sent (Bun closes a connection idle for 10 s). It ends after `done` (or `error`). A client that reconnects sends `Last-Event-ID: <last id seen>` and gets the events after it, none missed or repeated. `done` is sent only after the answer is written: a client that sees it and refetches reads the final message. A run's log stays readable for 10 minutes after it ends, then the route is 404 and the message is read through `conversation`. `stopRun(runId)` stops the run and returns the message STOPPED with the text written; on a finished run it returns the message unchanged. `@softistx/telemetry` stays a dependency: `aiTelemetry`, which watches every run (no content), needs it as a peer. The run design is single process (`IdleService` relies on it: an `activeRunId` that this process does not hold is stale and is released, which is only true because the deploy stops the old container before the new one serves): runs are claimed and followed in the API's memory, so a rolling deploy with two overlapping processes would treat each other's runs as stale. The deploy stops the old container before it starts the new one. Once the server begins to shut down, a send is refused (503 `auth.errors.unavailable`) and one already preparing its run ends FAILED `INTERRUPTED`. Runs and their log live in this process (one API container): a restart ends the runs it interrupted. At boot, before listening, every message still STREAMING becomes FAILED with `errorCode` `INTERRUPTED` and every `activeRunId` goes back to null; the same code is written when the server shuts down under a run. `errorCode` otherwise is the SDK's wire code (`MODEL_ERROR`, ...). Three codes are the API's own and internal (in no GraphQL error inventory): `INTERRUPTED` (the server went down under the run, decided per run: only an abort `abortAll` caused; a member's stop stays STOPPED), `TIMEOUT` (the run passed the longest a run may last, 10 minutes, `maxRunMs`) and `FINALISE_FAILED` (the answer could not be written when the run ended; the message and the conversation were released by hand, and a later send also releases, as FAILED `INTERRUPTED` (the likeliest cause is a crash the sweep missed), an `activeRunId` no run of the process holds). Each is one constant (`conversations.run-codes.ts`), used by the rules and the sweep. The stream route reads its first item before answering 200, so a run whose log expired meanwhile is a 404. `Conversation.activeRunId` is the id of the answer being written, null when idle: a send while it is set is 409 `run-in-progress`.

## Budgets

Each assistant message stores `usage` and `cost` (USD; Claude by the price table, Ollama 0, unknown price null) on every end path of a run (done, stopped, failed); a title or summary is not counted. The month is the calendar month in America/Toronto (`Intl`, an injected clock; `src/shared/months.ts`). **Spend is a ledger**: the `spend` collection (owned by conversations, figures only: owner, month, model, cost, tokens, reply count) is incremented with an `$inc` upsert in the same transaction that ends the assistant message, once per message with a cost or usage, in the Toronto month of the message's `createdAt` (the injected clock). It is kept after the conversation is purged, so a member's spend never shrinks when messages are deleted (spend before this ledger existed is not counted). The budgets read it through conversations' `SpendService`; no content is read. At 80 % one alert per member and month: a `budgetAlerts` document (unique `(memberId, month)`; the month is the one the run counted in, so a run that crossed midnight on the 1st is checked in the month it was spent in) which is the in-app notice (`budgetStatus.alertedAt`), a mail in the member's language, and the `onAlert` hook where push (slice 14) plugs in; checked in the background after a run's cost is written. The alert is recorded first (the unique index is the one-winner gate), then the mail is sent in the background: a failed send is logged and not retried, the alert staying recorded, so it is never sent twice. The mail template is budgets' own (`budgets.utils.ts`), not janus's: it is a notice to a known member, not a janus account mail. At 100 % a send, edit or regenerate to a paid model is refused (`budgets.errors.exhausted`) before the run is claimed. A run already started finishes and records its cost, so the spend may overshoot the budget by that run (and by runs in flight together); a run that was interrupted by a restart records no cost. The default budget lives in `budgetSettings` (one document, owned by budgets; slice 15 may fold it into the admin settings).

## Branches, search, export and deletion

Messages form a tree; a conversation shows one branch, `activeLeafId` its leaf, and the model reads the path from the first message to that leaf. `editMessage(messageId, text)` (a member's message only) writes a sibling under the same parent (the first message has a null parent, in a conversation that already has others) and a new reply; `regenerate(messageId, modelId?)` (an answer only) writes a sibling reply under the same member message, and a `modelId` (enabled) becomes the conversation's model. Both go through the send: its limit, its claim, the model and persona checks, and the same payload; the new branch becomes the one shown. `Message.siblings { ids, index }` lists the messages sharing a parent in creation order. `setActiveBranch(conversationId, messageId)` moves the leaf to the deepest one below the message (the latest child at each step) and is refused while a run is active (409 `run-in-progress`).

Search is `ConversationFilter.search` (documented cap: at most 500 conversations, the most recently written, deleted ones dropped before the cap): MongoDB text indexes on `conversations.title` and `messages.searchText` (the text parts only, never the reasoning), each led by `ownerId`, so another member's text never matches; the input is cut at 100 characters and 8 words, `"` and `\` and leading `-` are dropped and every word is a phrase (all must match in the same title or message, no operator is read). No snippet: the list is the usual connection, ordered by `lastMessageAt`, narrowed to at most 500 matches.

`exportConversation(id, MARKDOWN | JSON)` writes the branch shown (Markdown) or the whole tree with each message's `parentId` (JSON) to the private bucket under the `conversation-exports` kind and returns the media key; the file is `GET /media/conversation-exports/<key>`, always a download, readable by its owner only (the admin's read is 404), never uploaded over HTTP. A new export of the same conversation and format replaces the previous file.

`deleteConversation` is a soft delete, refused while a run really is active (409 `run-in-progress`: stop it first; a stale `activeRunId` that no run holds is released, as a send, a delete and `setActiveBranch` all do through one `IdleService`); `restoreConversation` brings it back within 30 days (409 `restore-expired` after, or once the purge has taken it: one conditional write). `ConversationsPurge` hard-deletes the conversations deleted more than 30 days ago, with their messages and exports (files and records), every 24 h from `server.ts` only (an explicit ticker, unref'd; a conversation that fails stays held and is retried once the hold is an hour old). Reactions are one per member per emoji, at most 20 a message (`react` toggles); `pinMessage` pins and `pinnedMessages` lists (documented cap: the first 100, oldest first).

The `conversation-exports` kind has `sniff: false` on purpose: its types, `text/markdown` and `application/json`, have no signature the media package can check (it refuses a kind that sniffs a type it cannot), and the file is written by the API, never uploaded. Messages written before this slice have an empty `searchText`, so a search does not find them: there is no data to keep on `feat/v1`, so no backfill is written. Conversations nothing was said in yet (no `activeLeafId`) are left out of both the live list and the trash, but a restore by id still brings one back. `ConversationFilter.deleted: true` lists the trash (deleted less than 30 days ago, the latest deletion first; `Conversation.purgeAt` says when each goes for good); an export is one file per conversation and format, readable only while the conversation is live, and `exportConversation` is limited to 10 an hour (burst 3, fails open).

## Attachments

The `attachments` module owns the `attachments` collection (`{ key, ownerId, kind: image | pdf | text, mime, bytes, name, extractedText?, truncated, conversationId?, messageId?, createdAt }`), the `attachments` media kind and the unlinked-upload sweep; conversations reach it through ports (`ConversationAttachments`), as they reach personas. It is its own module because a file exists before any message does and has its own read path.

`PUT /media/attachments` takes the file as the body and its name in the `x-file-name` header (percent-encoded; "attachment" when missing). It answers `{ id, key, contentType, size, kind, name }`; `id` is what `sendMessage` takes. Accepted: `image/jpeg`, `png`, `webp` up to 10 MiB, `image/gif` up to 3 932 160 bytes, `application/pdf`, `text/plain`, `text/markdown`, `text/csv` and `application/json` up to 20 MiB. The type is checked against the first bytes of the file for images and PDFs (`sniff: 'known'`, 415). A JPEG, PNG or WebP is re-encoded at upload into one WebP of at most 1568 px on its longer side (`withImageRendition`, `full`, quality 82) and the upload itself is never stored: the stored picture is far under Claude's 5 MB per image and its EXIF and GPS data are gone, so the record's `mime` is `image/webp`, `bytes` the stored size, and the file is read at `/media/attachments/<key>/full` (the bare key is 404). A GIF is the exception: `@softistx/image` decodes no GIF, so it is stored as sent (still `image/gif`, read at `/media/attachments/<key>`). Claude measures its 5 MB per-image limit on the base64, so a GIF is held to 3 932 160 bytes (413 above) and, as it is not resized, to 2000 px on a side, read from its header (the logical screen, bytes 6 to 9; 413 above). Images reach Ollama as WebP: check that the Ollama in use decodes WebP (0.4 and later do), else vision fails on that path. A text file has no signature, so after the store the upload hook reads the bytes back as a stream and refuses (415, file removed) any that is not strict UTF-8 (`TextDecoder` with `fatal: true`, `stream: true`, every byte checked) or that holds a NUL byte; only the first 100 000 characters are kept, in `extractedText` (`truncated: true` when there were more), so the buffer stays bounded. An image over 10 MiB is 413 (refused on the declared length, and again after the store when none was declared). Limits: the avatars' `media-uploads` count (30 an hour per account, burst 10, fails open, one shared helper `uploadThrottle`) and a quota of 200 files per member (402 `quota_exceeded`, checked before the body is read and counted again once the record is written, so two uploads racing past it cannot both stay). `GET /media/attachments/<key>` is the uploader's alone, and, once sent, only while the conversation is live (deleted conversation: 404 until restored); another member and the admin get 404, as does `attachment(id)`. There is no DELETE route: `deleteAttachment` (single-item, the UI's remove-chip) removes an unlinked upload (409 `in-use` once a message carries it): the record is claimed first by a conditional delete a send's link cannot pass, then the file is removed (a failure is logged and the orphan file is harmless).

`sendMessage` and `editMessage` take `attachmentIds` (at most 10, enforced by the SDL and again by the service; a repeated id is refused at the index of the repeat; an edit does not inherit the edited message's). Each id must be the member's own unlinked upload or one already in this conversation; any other is an issue on `attachmentIds.<i>` (`attachments.errors.not-attachable`) and the send is refused whole (all or nothing, nothing linked, nothing written). The budget check and the idle check run first. The link is checked inside the exchange's transaction (a file linked or swept meanwhile refuses the whole send; a call with no session is refused 409). The user message's `parts` get `{ type: "attachment", key, kind, name, mime, bytes }` after the text, and the files are linked (`conversationId`, `messageId`) in the exchange's transaction (a file already in the conversation keeps its first message).

What the model reads is built at run time (`AttachmentsService.expand`, files read from the bucket, never stored in messages): an image is an SDK `image` part for Claude and for an Ollama model with the `vision` capability; for any other Ollama model the image is dropped and a text note says so. A PDF's pages are counted at upload by a heuristic, without a parser: the occurrences of `/Type /Page` (not `/Pages`, whitespace tolerated) in its bytes, at least one, stored as `pages`; a PDF with a page tree inside a compressed object stream is undercounted. More than 100 pages is refused 413. A PDF is sent whole as a `document` part to Claude; **PDF text extraction is not done**: no extractor exists in any dependency or `@softistx/ai-*` (softistx/ai#220 asks for one), so until #220 ships every non-Claude model gets a short text note instead of the PDF and `extractedText` stays null for PDFs. One request carries at most 20 MiB of raw image and PDF bytes, 20 images and 100 PDF pages, newest occurrence first (each occurrence is counted, each file read once) (base64 grows them by a third; Claude's limit is 32 MB): older files past it become a text note. Files are read from the bucket four at a time; a record whose object is gone from the bucket is a "no longer available" note, never an error. Every note and text file block starts with a blank line, because ai-ollama joins the text parts of a message with nothing. A text file is sent as text under its name, with a note when it was truncated. The fold of an older context (`compact`) sees an attachment as `[Attachment: name]`; the context is folded first, then the estimate of the kept messages' attachments (`IMAGE_TOKENS` per image, 2000 tokens a PDF page (`DOCUMENT_TOKENS` when its pages are unknown), a quarter of the bytes of a text file, bounded) is added to the kept tokens and, when that passes the budget, folded once more to what is left of it (attachments of folded messages cost nothing). The real cost is the provider's usage.

The conversation purge deletes a conversation's attachments (files, then records) with it; the same tick sweeps the uploads no message carried within 24 hours (`AttachmentsPurge`, record claimed first, then the file).

## Memory

The `memory` module owns `memoryItems` (`{ ownerId, personaId, text (1 to 500 characters), source: model | user }`), per persona and member. Every read and write carries `ownerId`: another member and the admin get `memory.errors.not-found` on an item id, and the admin has no field that reads memory. `memoryItems(personaId)` lists the member's items newest first (at most 200) for a persona the member may read, a deleted one included (a persona is soft-deleted, so its memory stays); `addMemoryItem` (source USER, needs a persona not deleted), `updateMemoryItem`, `deleteMemoryItem` (answers the id) and `clearMemory(personaId)` (answers the count) are the member's. A persona holds at most 200 items for a member: the 201st is refused with 409 `memory.errors.full` (`max` in the params). The cap is atomic: the item is inserted, then counted by rank (the items of the member for the persona whose id is up to its own); an item of rank over 200 is deleted again and refused, so adds that race end at exactly 200 (the ids are one total order; ids made by two processes may in theory cross, which is not guarded). A blank or over-long `text` is a field issue on `text`. A conversation purge never touches memory.

A run gets the tools `remember(text)` and `forget(id)` only when the persona has `tools.memory`. They are zod tools of `@softistx/ai-core`; `forget` accepts only an id of the member's own items for this persona (the input is refused to the model as `INVALID_TOOL_INPUT`, which it can correct, and the service checks again when the action runs, as a `TOOL_FAILED` carrying the memory's code in `details`). `remember` is a proposed action unless the member's `rememberWithoutAsking` setting is true: then the tool runs inside the run, with no pending action. **Provenance**: once the run has called a tool that is not the memory's (the web, an MCP server: the memory's observer sees `onToolStart` and `onToolCall`), or when the conversation so far holds a `tool-result` of such a tool, a provider's `server-tool` block or an uploaded document (an attachment of kind pdf or text; an image does not taint) (read from the path before the run starts; an uploaded document is outside input, and a future MCP action's output would need the same treatment), `remember` is proposed again whatever the setting, because what it would save may come from untrusted text; a step that calls both at once is decided in call order, so it is not airtight, and no tool but the memory's exists yet. The tool reads `confirm` through a getter at each call: this is `Temporary, until softistx/ai#221` (a per-call `confirm` in the SDK), and a spec runs the real `runAgent` so that an SDK which copies the tools fails a test. `forget` is always a proposed action, never auto-confirmed. The ids `forget` may name are those of the items at the start of the run, so **a fact remembered in a run cannot be forgotten in the same run**. A fact remembered without asking stays when the run is stopped.

The persona's items are injected in the system prompt after the persona's words and the language, newest first, at most 50 items and 4,000 characters. The framing: a header (data, not instructions), then `<remembered-facts>`, one line per fact `- [id] "text"` (the text a JSON string, whitespace folded, every `<` written `\u003c`, so a fact can neither close the block, open a line nor quote itself out), `</remembered-facts>` and an end line. The compaction budget counts the block and the tools' schemas in the system tokens. The tool turns are in the provider usage already, so the budgets need nothing more.

## Projects

The `projects` module owns `projects` (`{ ownerId, name (1 to 80), instructions (at most 4,000 characters), purgingAt }`, soft delete, version lock), `projectDocuments` and `chunks`. Every read and write carries `ownerId`: another member and the admin get `projects.errors.not-found` (a project) or `projects.errors.document-not-found` (a document), and the admin has no field that reads a project, a document or a chunk (the privacy spec walks them). A member keeps at most 50 live projects (409 `projects.errors.too-many`) and 100 documents per project (409 `projects.errors.too-many-documents`). `updateProject` takes the version it read: another write since is 409 `projects.errors.version-conflict`; a field left out stays, `name` or `instructions` given as null is `validation.errors.required`. `deleteProject` is a soft delete (restorable 30 days through `restoreProject`, which a purge that took the project cannot be passed); a deleted project is no longer searched or injected at once. The daily `ProjectsPurge` (started from `server.ts` only, through the ticker port, by a conditional `purgingAt` claim a restore cannot pass) removes the files, then the documents, then the chunks, then the project, and exposes nothing of their content. A conversation joins a project with `setConversationProject(id, projectId)` (null leaves it; the project must be the member's own and live) and lists by `filter.projectId`. A persona binds projects through `projectIds`: each must be the member's own live project (`projects.errors.not-found` on `projectIds.<i>`); a TEAM persona's foreign ids are ignored by a run (the project is looked up by the viewer's id), and a duplicate drops them.

**Documents** are their own kind of upload, not attachments: `PUT /media/project-documents` takes the file as the body, its name in `x-file-name` and the project's id in `x-project-id`, and answers `{ id, key, contentType, size, name, status }`. Accepted: `text/plain` and `text/markdown` up to 10 MiB, `application/pdf` up to 20 MiB (the first bytes of a PDF are checked, 415); the upload throttle is the attachments' (`uploadThrottle`). `GET /media/project-documents/<key>` is the uploader's alone while the project is live; another member and the admin get 404. A document that is not a text file of valid UTF-8 ends FAILED `NOT_TEXT`. There is no DELETE route: `deleteProjectDocument(id)` removes its chunks, its file and its record. **A PDF is stored and kept FAILED with `errorCode` `PDF_TEXT_UNAVAILABLE`, never indexed**: no text extraction exists in any dependency or `@softistx/ai-*` (softistx/ai#220 asks for one), and none is built here; `reindexProjectDocument` refuses a PDF. When #220 ships, a PDF is indexed through it and the FAILED ones are reindexed by a script.

**Indexing** is a background job. An upload records the document PENDING and adds a job to the `indexing` queue (`@softistx/redis` `defineQueue`, `src/config/queues.ts`: 3 attempts, 5 s then 10 s backoff, 10 minute timeout; the payload is the document id only). `IndexingWorker` (started from `server.ts` only, one job at a time) reads the file from the bucket, cuts it (`chunkText`, about 800 tokens of 4 characters with an overlap of 100, cut at a paragraph, line, sentence or space), embeds the chunks 16 at a time and writes them with the owner and project; the document is then INDEXED with its `chunkCount`. Indexing again replaces the chunks of the document ((document, ordinal) is their identity). A failure that would repeat ends the document FAILED at once (`NOT_TEXT`, `EMPTY_DOCUMENT`, `FILE_MISSING`, `PDF_TEXT_UNAVAILABLE`); any other (`EMBEDDINGS_UNAVAILABLE` when `EMBED_BASE_URL` is unset, else `INDEXING_FAILED`) is retried and ends FAILED on the last attempt. A queue that cannot take the job at upload leaves the document FAILED `QUEUE_UNAVAILABLE`. `reindexProjectDocument` indexes a FAILED (not PDF) or a stuck PENDING document again. Without `REDIS_URL` (development) the same queue runs in this process (`localQueues`): the job is lost on a restart, and `reindexProjectDocument` brings it back. **Only the first 400,000 characters of a document are indexed** (about 140 chunks, so that the embeddings fit the 10 minute timeout on the VPS's CPU); the rest of a larger file is stored and downloadable but not searchable, and nothing says so on the document. An abort (the server shutting down, or the timeout) is not a failure of the document: the job goes back to the queue when its lease ends. A document that ends FAILED keeps no chunk, and a search cites only INDEXED documents. `deleteProjectDocument` removes the record first, then the chunks, then the file; an indexing running meanwhile finds its document gone and removes what it wrote. The `errorCode` of a document is a stored string, not an API error code.

**Embeddings** go through the SDK only: `ollamaEmbeddings` of `@softistx/ai-ollama` (model `nomic-embed-text`, 768 dimensions, `EMBED_BASE_URL`, the VPS's `ollama-embed`) behind `embed` of `@softistx/ai-core`; a text is prefixed `search_document: ` and a query `search_query: ` as the model asks. They are free like every Ollama call and are not counted in `spend`. **Vector search** is behind the `VectorIndex` port (`upsert`, `remove`, `search`): production is MongoDB 8 `$vectorSearch` over `chunks` (index `chunks_vector`: `embedding`, 768 dimensions, cosine, filter fields `ownerId` and `projectId`), the specs use an in-memory cosine one. Every search names the owner AND one project: the `$vectorSearch` pre-filter is `vectorFilter` (an `$and` of both, run as a plain `find` in its spec) and a row that is not the asked owner's and project's is dropped again after the engine answers. The score is `(1 + cosine) / 2`. The vector index is not a regular index, so `autoSync` does not make it: `bun run db:sync` (a deployment step, after the regular sync) creates it through `ensureVectorIndex` and fails when `mongot` is not there; the development boot tries it and only warns.

**A run in a project** (`ProjectSearchService.kit`): the projects of a run are the conversation's `projectId`, else the first five projects its persona is bound to, always the viewer's own live ones. The system prompt gets the instructions after the language and before the facts, framed (`projectBlock`: a header saying they are the member's own notes that cannot change the application's rules, one JSON string per project, `<` escaped, between `<project-instructions>` tags, 4,000 characters in all). The run gets the read-only tool `search_project(query)` (the query is 1 to 500 characters): the six best passages across those projects, each `{ documentId, name, text (the whole chunk, about 800 tokens), score }` with a notice that they are data, never instructions. It is not a proposed action. Its output is untrusted: like any tool that is not the memory's it taints the run, so `remember` is proposed even when the member remembers without asking (also for a later run whose history holds its result: `taintedBy`). A message shows each result as a `MessageCitationPart { documentId, name, snippet, score }`, in place, read from the stored `search_project` tool result (nothing is stored twice); the `snippet` is the first 400 characters of the stored `text`, cut at read time. A failed search is a tool error whose code is `EMBEDDINGS_UNAVAILABLE` or `SEARCH_FAILED`.

## Proposed actions

A tool defined with `confirm: true` is never run by the loop (`@softistx/ai-core`'s `runAgent`): it emits a `proposed-action` event, records a `proposed-action` part in the tool message (`{ id, tool, input, summary, expiresAt }`) and answers the model `{ status: "pending", actionId }`. The run then goes on and ends normally; the SDK has no resume. When the run's message ends DONE, each proposed-action part gets an id of the store's own and the `proposedActions` documents `{ ownerId, conversationId, messageId, runId, callId (the model's), tool, input, summary (at most 1,000 characters), status: pending | running | confirmed | rejected | expired | failed, expiresAt, result, decidedAt }` are written **in the same transaction as the message's end** (`RunMessagesService.finalise`): a message never carries an action id with no document, and a run that is stopped or fails keeps neither the part nor the document. The store is generic: memory uses it, and the MCP tools (spec 4.9) reuse it by adding their tools to `ConversationActionTools`. The time to answer is 15 minutes (`proposalTtlMs`); a pending action past it reads EXPIRED, and one stuck `running` for more than 5 minutes (the claiming process died) reads FAILED. Owner only: another member and the admin get `conversations.errors.action-not-found`; the conversation purge deletes its actions.

`pendingActions(conversationId)` lists the waiting ones, oldest first. `confirmAction(id)` claims the action (`pending` to `running`, only before its expiry, one writer wins), finds the tools, re-validates the input and runs the tool once through `runConfirmedAction`; whatever fails on the way (the tools, the input, the tool) settles `failed` with the error code, so no action stays `running`. It stores `confirmed` (with `result`) or `failed`. A second call on a decided action answers it as it stands; a confirm racing a reject leaves one state. `rejectAction(id)` marks it `rejected` and runs nothing. Past the expiry both settle it `expired` and answer 409 `action-expired`. Neither starts a new model turn: the member writes the next message.

**What the model reads.** A run's answer is stored with its `turns` (`[{ role: assistant | tool, count }]`, the grouping of its parts in the SDK's messages), so the history sent back is valid: assistant (text, tool calls), tool (tool results, proposed actions: the result still says `pending`), assistant (text); parallel calls share one assistant turn and one tool turn, and a max-steps answer may end on a tool turn, followed by the member's message. A message with no turns (older, or whose turns do not add up to its parts) is flat and loses its tool parts in the history. The context always starts on a member's message: the assistant and tool turns a fold leaves at its head are dropped up to the first member message (the stored summary stands for what came before).

**Outcomes.** Each decided action (confirmed, rejected, failed, expired; a pending or running one says nothing yet) is told to the model by the SDK's `actionOutcomeMessage` text, at the head of a member message (a text part before the member's own; never a second `tool_result`). Where, from the path alone: the first member message on the current path created after the decision instant (`decidedAt`; the expiry for an action that ran out of time; `updatedAt` plus 5 minutes for a stale `running` claim). So every run on a path repeats it in the same place, a message that was created before the decision is never changed (the prompt prefix stays stable), a branch from before the proposing answer sees none, and a path with no later member message says nothing until the next send, whose message is the one. Nothing is stored for it. One active run per conversation is what keeps these reads consistent. A `running` claim stuck for 5 minutes is frozen `failed` (a conditional write, when the outcomes are read), so a late settle matches nothing and the told status never flips (a freeze that wins over a tool that did run records `failed`, so the model may remember the same fact twice); before it is read, the status shown reads `failed` and the claim can still settle `confirmed`. The outcome is recorded on the action document only: no `tool-result` part is added to the message after a confirm, and `shownParts` shows the status of the card. A stored context summary is anchored on a whole message only (`summaryAnchor`): a fold that ends inside an answer's turns serves that run only and is not stored (`Temporary, until softistx/ai#222`, a cut predicate for `compact`), so the next run folds again: one extra summarise call per run in that case, and the summary text changes between runs. The kept context starts on a member's message: a leading `tool` turn whose call was folded is dropped, and a context that would start on an assistant turn is given a short member turn first ("(Earlier conversation summarised above.)"), so no answer text is lost. `Message.parts` has `MessageProposedActionPart { actionId tool summary status }` (the status read live, batched by one DataLoader per request), which the UI renders as a confirmation card calling `confirmAction` or `rejectAction`.

The SSE events of a run (`GET /runs/<runId>/events`, one frame per `@softistx/ai-core` event, named after its type) now also carry `tool-call` (the model's call, before it runs), `tool-result` (`{ result }`, a tool that ran or the `pending` answer of a proposal) and `proposed-action` (`{ action: { id, tool, input, summary, expiresAt } }`, `id` the model's call id, not the `actionId` of the message: the confirmation card is drawn from the final message after `done`).
