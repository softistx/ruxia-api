# Domain glossary

ruxia is a messaging app whose contacts are AI personas. The code, the GraphQL schema and
the collections speak English; the people who use it speak French, often. Each term is the
one the code uses, with the French it stands for. A term joins this table with the module
that introduces it. The specification is [docs/spec.md](docs/spec.md).

| Term (code)      | French                | Meaning                                                                                                                                                                     |
| ---------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Member           | membre                | A person with an account on this ruxia; `members` holds its name, locale, avatar and settings. Its id is the janus account's.                                               |
| Role             | rôle                  | `admin` or `member`, held in janus's relations, never stored on the member. The last active admin cannot be demoted or disabled.                                            |
| Invitation       | invitation            | The only way in: an admin invites an address with a role; the invitee accepts with a name and a password. No sign-up.                                                       |
| Disabled         | désactivé             | A member with `disabledAt` set: janus refuses its sessions and sign-ins until an admin enables it.                                                                          |
| Viewer           | utilisateur           | The signed-in member as the session shows it: role, locale, second factor, passkeys, budget status.                                                                         |
| MemberSettings   | réglages              | Language fr/en, push previews, voice auto-play, default persona, "remember without asking" (spec 4.16).                                                                     |
| BudgetStatus     | budget                | Where the member stands this month (`viewer.budgetStatus`): spent, budget, percent, `alertedAt` (the in-app notice of the 80 % alert), `resetsAt`.                          |
| Budget           | budget mensuel        | USD per member per calendar month in America/Toronto: its own (`setMemberBudget`) or the team default (`setDefaultBudget`, 20 until set). 0 allows no paid model.           |
| Usage            | consommation          | `usage(month)` and the admin's `teamUsage(month)`: cost and tokens per member and per model, figures only. The month is `YYYY-MM`.                                          |
| Model            | modèle                | An entry of the model catalogue (`models`): public id, provider (Claude or Ollama), label, capabilities, context window, prices.                                            |
| Enabled          | activé                | A model an admin allows conversations to use. Claude models start enabled; discovered Ollama models start disabled.                                                         |
| Available        | disponible            | A model a send can reach now: always for Claude, for Ollama while the last probe saw its server up with the model installed.                                                |
| Probe            | sonde                 | The check of the Ollama server every 30 s (`OLLAMA_BASE_URL`), cached in Redis for 90 s, which also lists new installed models.                                             |
| Persona          | persona               | An AI contact a member creates (`personas`): name, avatar, tagline, personality (the system prompt), default model, tools.                                                  |
| Visibility       | visibilité            | `PRIVATE` (the owner only) or `TEAM` (every member reads and starts it, only the owner edits; others duplicate it into a PRIVATE copy).                                     |
| Catalogue        | catalogue             | The TEAM personas, read with `catalogue(filter)`; the admin features some and orders them (`setPersonaFeatured`, `reorderFeatured`).                                        |
| Featured         | mis en avant          | A TEAM persona the admin placed (`featuredRank`) at the top of the catalogue. Making it PRIVATE again unfeatures it.                                                        |
| Conversation     | conversation          | A member's exchange with one persona (`conversations`): model, title, snapshot of the persona, `activeLeafId`. Private to its owner, the admin included.                    |
| Message          | message               | A node of a conversation's tree (`messages`): `parentId` links it to the message it follows; several children make branches.                                                |
| Run              | exécution             | The writing of one assistant answer, started by `sendMessage`; its id is the assistant message's id (`Message.runId` while STREAMING), held as `activeRunId` until it ends. |
| Active leaf      | feuille active        | The last message of the branch a conversation shows; the path from the root to it is what the model reads and the list pages.                                               |
| Persona snapshot | instantané du persona | The persona's name and avatar kept on the conversation when it starts, so it stays readable after a rename or delete.                                                       |
| Attachment       | pièce jointe          | A file (image, PDF or text) a member uploads to send with a message; a message keeps a reference, never a URL.                                                              |

Modules: `accounts` (sign-in, second factor, passkeys, step-up), `members`, `invitations`,
`models`, `personas`, `conversations`, `budgets`, `translations` and `system`. Operator scripts: `admin:create <email>` (issues an admin
invitation and mails it; `--print-link` prints the link), `db:sync`, `db:migrate`,
`schema:print`.

## Media

Files go through `@softistx/alxia-media` routes beside `/graphql`, over the private `S3_*` bucket (no URL ever leaves the API; the UI builds `/media/<kind>/<key>/<size>` on its own origin). Three kinds share the one mount (`appMedia`): `attachments` (below, under "Attachments"), `conversation-exports` (below, under "Branches, search, export and deletion") and `persona-avatars` (`PUT` and `GET`, no `DELETE`; png, jpeg or webp up to 2 MiB, at least 64 px a side). A `PUT` answers `{ key, contentType, size }`. The upload is re-encoded into PNG squares of 256 and 64 px and never stored, so its EXIF and GPS data are dropped: only `/media/persona-avatars/<key>/256` and `/64` are served (the bare key is 404). The key is the uploader's until a persona carries it, then read by the persona's readers. Limits: `media-uploads` 30 an hour per account (burst 10, fails open) and a quota of 50 files per member (402 `quota_exceeded`). An upload whose key cannot be recorded is removed at once. Files are otherwise kept: a deleted persona keeps its avatar.

## Runs

`sendMessage` writes the member's message (DONE) and an empty assistant message (STREAMING), makes `runId` the assistant message's id, sets it as the conversation's `activeRunId` and starts the run, which goes on whether or not the client stays. The answer is followed at `GET /runs/<runId>/events`, the second transport beside `/graphql` (after `/media`): the same viewer (`Authorization: Bearer`) and the `x-ruxia-client` header, and the answers are the API's JSON, `{ errors: [..] }`: 403 `auth.errors.client-header-required`, 401 `auth.errors.unauthenticated`, 403 `auth.errors.forbidden` (no role), 404 `conversations.errors.run-not-found`. The stream is `text/event-stream`: one frame per event, named after its type (`step-start`, `text-delta`, `thinking-delta`, `usage`, `error`, `done`, ...), with `id:` the event's position in the run (`1`, `2`, `3`, ...) and `data:` its JSON; a `: heartbeat` comment every 5 s while nothing is sent (Bun closes a connection idle for 10 s). It ends after `done` (or `error`). A client that reconnects sends `Last-Event-ID: <last id seen>` and gets the events after it, none missed or repeated. `done` is sent only after the answer is written: a client that sees it and refetches reads the final message. A run's log stays readable for 10 minutes after it ends, then the route is 404 and the message is read through `conversation`. `stopRun(runId)` stops the run and returns the message STOPPED with the text written; on a finished run it returns the message unchanged. `@softistx/telemetry` stays a dependency: `aiTelemetry`, which watches every run (no content), needs it as a peer. The run design is single process (`IdleService` relies on it: an `activeRunId` that this process does not hold is stale and is released, which is only true because the deploy stops the old container before the new one serves): runs are claimed and followed in the API's memory, so a rolling deploy with two overlapping processes would treat each other's runs as stale. The deploy stops the old container before it starts the new one. Once the server begins to shut down, a send is refused (503 `auth.errors.unavailable`) and one already preparing its run ends FAILED `INTERRUPTED`. Runs and their log live in this process (one API container): a restart ends the runs it interrupted. At boot, before listening, every message still STREAMING becomes FAILED with `errorCode` `INTERRUPTED` and every `activeRunId` goes back to null; the same code is written when the server shuts down under a run. `errorCode` otherwise is the SDK's wire code (`MODEL_ERROR`, ...). Three codes are the API's own and internal (in no GraphQL error inventory): `INTERRUPTED` (the server went down under the run, decided per run: only an abort `abortAll` caused; a member's stop stays STOPPED), `TIMEOUT` (the run passed the longest a run may last, 10 minutes, `maxRunMs`) and `FINALISE_FAILED` (the answer could not be written when the run ended; the message and the conversation were released by hand, and a later send also releases, as FAILED `INTERRUPTED` (the likeliest cause is a crash the sweep missed), an `activeRunId` no run of the process holds). Each is one constant (`conversations.run-codes.ts`), used by the rules and the sweep. The stream route reads its first item before answering 200, so a run whose log expired meanwhile is a 404. `Conversation.activeRunId` is the id of the answer being written, null when idle: a send while it is set is 409 `run-in-progress`.

## Budgets

Each assistant message stores `usage` and `cost` (USD; Claude by the price table, Ollama 0, unknown price null) on every end path of a run (done, stopped, failed); a title or summary is not counted. The month is the calendar month in America/Toronto (`Intl`, an injected clock; `src/shared/months.ts`). **Spend is a ledger**: the `spend` collection (owned by conversations, figures only: owner, month, model, cost, tokens, reply count) is incremented with an `$inc` upsert in the same transaction that ends the assistant message, once per message with a cost or usage, in the Toronto month of the message's `createdAt` (the injected clock). It is kept after the conversation is purged, so a member's spend never shrinks when messages are deleted (spend before this ledger existed is not counted). The budgets read it through conversations' `SpendService`; no content is read. At 80 % one alert per member and month: a `budgetAlerts` document (unique `(memberId, month)`; the month is the one the run counted in, so a run that crossed midnight on the 1st is checked in the month it was spent in) which is the in-app notice (`budgetStatus.alertedAt`), a mail in the member's language, and the `onAlert` hook where push (slice 14) plugs in; checked in the background after a run's cost is written. The alert is recorded first (the unique index is the one-winner gate), then the mail is sent in the background: a failed send is logged and not retried, the alert staying recorded, so it is never sent twice. The mail template is budgets' own (`budgets.utils.ts`), not janus's: it is a notice to a known member, not a janus account mail. At 100 % a send, edit or regenerate to a paid model is refused (`budgets.errors.exhausted`) before the run is claimed. A run already started finishes and records its cost, so the spend may overshoot the budget by that run (and by runs in flight together); a run that was interrupted by a restart records no cost. The default budget lives in `budgetSettings` (one document, owned by budgets; slice 15 may fold it into the admin settings).

## Branches, search, export and deletion

Messages form a tree; a conversation shows one branch, `activeLeafId` its leaf, and the model reads the path from the first message to that leaf. `editMessage(messageId, text)` (a member's message only) writes a sibling under the same parent (the first message has a null parent, in a conversation that already has others) and a new reply; `regenerate(messageId, modelId?)` (an answer only) writes a sibling reply under the same member message, and a `modelId` (enabled) becomes the conversation's model. Both go through the send: its limit, its claim, the model and persona checks, and the same payload; the new branch becomes the one shown. `Message.siblings { ids, index }` lists the messages sharing a parent in creation order. `setActiveBranch(conversationId, messageId)` moves the leaf to the deepest one below the message (the latest child at each step) and is refused while a run is active (409 `run-in-progress`).

Search is `ConversationFilter.search` (documented cap: at most 500 conversations, the most recently written, deleted ones dropped before the cap): MongoDB text indexes on `conversations.title` and `messages.searchText` (the text parts only, never the reasoning), each led by `ownerId`, so another member's text never matches; the input is cut at 100 characters and 8 words, `"` and `\` and leading `-` are dropped and every word is a phrase (all must match in the same title or message, no operator is read). No snippet: the list is the usual connection, ordered by `lastMessageAt`, narrowed to at most 500 matches.

`exportConversation(id, MARKDOWN | JSON)` writes the branch shown (Markdown) or the whole tree with each message's `parentId` (JSON) to the private bucket under the `conversation-exports` kind and returns the media key; the file is `GET /media/conversation-exports/<key>`, always a download, readable by its owner only (the admin's read is 404), never uploaded over HTTP. A new export of the same conversation and format replaces the previous file.

`deleteConversation` is a soft delete, refused while a run really is active (409 `run-in-progress`: stop it first; a stale `activeRunId` that no run holds is released, as a send, a delete and `setActiveBranch` all do through one `IdleService`); `restoreConversation` brings it back within 30 days (409 `restore-expired` after, or once the purge has taken it: one conditional write). `ConversationsPurge` hard-deletes the conversations deleted more than 30 days ago, with their messages and exports (files and records), every 24 h from `server.ts` only (an explicit ticker, unref'd; a conversation that fails stays held and is retried once the hold is an hour old). Reactions are one per member per emoji, at most 20 a message (`react` toggles); `pinMessage` pins and `pinnedMessages` lists (documented cap: the first 100, oldest first).

The `conversation-exports` kind has `sniff: false` on purpose: its types, `text/markdown` and `application/json`, have no signature the media package can check (it refuses a kind that sniffs a type it cannot), and the file is written by the API, never uploaded. Messages written before this slice have an empty `searchText`, so a search does not find them: there is no data to keep on `feat/v1`, so no backfill is written. Conversations nothing was said in yet (no `activeLeafId`) are left out of both the live list and the trash, but a restore by id still brings one back. `ConversationFilter.deleted: true` lists the trash (deleted less than 30 days ago, the latest deletion first; `Conversation.purgeAt` says when each goes for good); an export is one file per conversation and format, readable only while the conversation is live, and `exportConversation` is limited to 10 an hour (burst 3, fails open).

## Attachments

The `attachments` module owns the `attachments` collection (`{ key, ownerId, kind: image | pdf | text, mime, bytes, name, extractedText?, truncated, conversationId?, messageId?, createdAt }`), the `attachments` media kind and the unlinked-upload sweep; conversations reach it through ports (`ConversationAttachments`), as they reach personas. It is its own module because a file exists before any message does and has its own read path.

`PUT /media/attachments` takes the file as the body and its name in the `x-file-name` header (percent-encoded; "attachment" when missing). It answers `{ id, key, contentType, size, kind, name }`; `id` is what `sendMessage` takes. Accepted: `image/jpeg`, `png`, `webp` up to 10 MiB, `image/gif` up to 5 MiB, `application/pdf`, `text/plain`, `text/markdown`, `text/csv` and `application/json` up to 20 MiB. The type is checked against the first bytes of the file for images and PDFs (`sniff: 'known'`, 415). A JPEG, PNG or WebP is re-encoded at upload into one WebP of at most 1568 px on its longer side (`withImageRendition`, `full`, quality 82) and the upload itself is never stored: the stored picture is far under Claude's 5 MB per image and its EXIF and GPS data are gone, so the record's `mime` is `image/webp`, `bytes` the stored size, and the file is read at `/media/attachments/<key>/full` (the bare key is 404). A GIF is the exception: `@softistx/image` decodes no GIF, so it is stored as sent (still `image/gif`, read at `/media/attachments/<key>`), held to 5 MiB. A text file has no signature, so after the store the upload hook reads the bytes back as a stream and refuses (415, file removed) any that is not strict UTF-8 (`TextDecoder` with `fatal: true`, `stream: true`, every byte checked) or that holds a NUL byte; only the first 100 000 characters are kept, in `extractedText` (`truncated: true` when there were more), so the buffer stays bounded. An image over 10 MiB is 413 (refused on the declared length, and again after the store when none was declared). Limits: the avatars' `media-uploads` count (30 an hour per account, burst 10, fails open, one shared helper `uploadThrottle`) and a quota of 200 files per member (402 `quota_exceeded`, checked before the body is read and counted again once the record is written, so two uploads racing past it cannot both stay). `GET /media/attachments/<key>` is the uploader's alone, and, once sent, only while the conversation is live (deleted conversation: 404 until restored); another member and the admin get 404, as does `attachment(id)`. There is no DELETE route: `deleteAttachment` (single-item, the UI's remove-chip) removes an unlinked upload (409 `in-use` once a message carries it): the record is claimed first by a conditional delete a send's link cannot pass, then the file is removed (a failure is logged and the orphan file is harmless).

`sendMessage` and `editMessage` take `attachmentIds` (at most 10, enforced by the SDL and again by the service; a repeated id is refused at the index of the repeat; an edit does not inherit the edited message's). Each id must be the member's own unlinked upload or one already in this conversation; any other is an issue on `attachmentIds.<i>` (`attachments.errors.not-attachable`) and the send is refused whole (all or nothing, nothing linked, nothing written). The budget check and the idle check run first. The link is checked inside the exchange's transaction (a file linked or swept meanwhile refuses the whole send; a call with no session is refused 409). The user message's `parts` get `{ type: "attachment", key, kind, name, mime, bytes }` after the text, and the files are linked (`conversationId`, `messageId`) in the exchange's transaction (a file already in the conversation keeps its first message).

What the model reads is built at run time (`AttachmentsService.expand`, files read from the bucket, never stored in messages): an image is an SDK `image` part for Claude and for an Ollama model with the `vision` capability; for any other Ollama model the image is dropped and a text note says so. A PDF is sent whole as a `document` part to Claude; **PDF text extraction is not done**: no extractor exists in any dependency or `@softistx/ai-*` (softistx/ai#220 asks for one), so until #220 ships every non-Claude model gets a short text note instead of the PDF and `extractedText` stays null for PDFs. One request carries at most 20 MiB of raw image and PDF bytes, newest first (base64 grows them by a third; Claude's limit is 32 MB): older files past it become a text note. Files are read from the bucket four at a time; a record whose object is gone from the bucket is a "no longer available" note, never an error. Every note and text file block starts with a blank line, because ai-ollama joins the text parts of a message with nothing. A text file is sent as text under its name, with a note when it was truncated. The fold of an older context (`compact`) sees an attachment as `[Attachment: name]`; the context is folded first, then the estimate of the kept messages' attachments (`IMAGE_TOKENS` per image, `DOCUMENT_TOKENS` per PDF, a quarter of the bytes of a text file, bounded) is added to the kept tokens and, when that passes the budget, folded once more to what is left of it (attachments of folded messages cost nothing). The real cost is the provider's usage.

The conversation purge deletes a conversation's attachments (files, then records) with it; the same tick sweeps the uploads no message carried within 24 hours (`AttachmentsPurge`, record claimed first, then the file).
